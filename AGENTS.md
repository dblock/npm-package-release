# Working on npm-package-release

Read [CONTRIBUTING.md](CONTRIBUTING.md) and [DESIGN.md](DESIGN.md) before making changes. This package ports reusable npm release operations from `ruby-gem-release`; it is not a general release service. Defer workspaces, alternate registries/hosts, and prerelease channels. See [Detailed Usage](docs/usage.md) for the actual CLI/API, hooks, and recovery contract.

## Implementation and Validation

Put strict TypeScript implementation in `src/`, compile ESM JavaScript/declarations/source maps into ignored `dist/`, keep the executable in `bin/`, unit tests in `test/`, compile-time contract tests in `test/types/`, and actual packed-consumer tests in `test/integration/`. Run `npm run build` before direct test/CLI invocation; `npm test` and package validation build automatically. Keep `npm-package-release` as the repository and npm package name; use `npr` for the CLI and `npr.config.js` for its configuration module. Support Node.js 22.14+, 24, and 26+; use Node.js 26 and npm 12 for development. Keep consumer engine checks strict and separate from development-tool requirements. Use public Node.js, npm, Git, and GitHub interfaces. Verify and prefer current stable tool/dependency releases while retaining supported-runtime compatibility.

Run `npm test` and `npm run lint` locally before every push, including PR updates. Run `npm run test:coverage` to inspect line/branch coverage; aim near full coverage during initial implementation, especially real error paths, without trivial assertions or hiding implementation code. Run `npm run test:package` before committing packaging/public-entry changes; inspect and install the real archive, not just source files. Reuse final pre-commit results for a push only when the tested content/configuration is unchanged. See CONTRIBUTING for provided, unset, and empty archive-override checks.

Preserve clean-checkout and trusted-staging boundaries, immutable release identity, reproducible exact-artifact publication, nonempty release notes, conflicting-output guards, atomic release pushes, and recovery after partial failure. Never retry publication automatically or validate the advanced manifest instead of the released artifact. Test ordering and real Git/npm consumers with simulated remote publication, not live publishing workflows or mocked consumer installation. Isolate GitHub environments and job summaries in simulations. Keep reusable/composite CLI behavior consistent and preserve failure-aware uploads; do not make a pinned workflow depend on a moving action reference.

Compose class-based `Step<Input, Output>` contracts with typed lifecycle records, not an untyped shared bag. Keep the runner provider-independent and accept service instances directly in workflow options. CLI modules and release API calls require workflow instances, not configuration objects. Default numeric notes to `KeepAChangelog`; select `IntrideaChangelog` or custom classes explicitly. Do not restore format objects, hosting flags, legacy validation hooks, separate service-argument adapters, or other unreleased compatibility paths. Do not weaken contracts with `any`, hide failed negative type tests, or assume types prove arbitrary custom steps preserve release safety. Test custom composition, replacement services, frozen records, and installed declarations as described in [Composable Workflows](docs/workflows.md).

Keep lifecycle hook registries immutable and invocation failures isolated. Preparation hooks belong inside trusted staging; other hooks may not smuggle edits into commits. Preserve original exceptions, report hook identity, skip hooks for disabled operations, and suppress whole-release success during preparation. Exercise hook order, retry/reconciliation, numeric/semantic workflows, and installed consumer/type contracts; see [Lifecycle Hooks](docs/hooks.md).

Keep changelog templates on class instances, preserving Keep a Changelog defaults. Strip prompts only outside opaque Markdown examples, reject prompt-only notes before writing, preserve references/source offsets, and restore only the intended category template. Intridea accepts multiple prompts and carries one-level headings into development; see [Changelog Templates](docs/changelogs.md).

Use the shared Markdown parser for section edits, not regular expressions over whole documents. Keep both `replace(body, options)` and section-scoped `replace(search, replacement, options)` on `MarkdownSection`. Preserve exact-heading checks, source offsets, surrounding content, newline style, and pre-write validation; see [Updating Markdown Sections](docs/markdown.md).

Keep the public testing API on the optional `npm-package-release/testing` subpath with no test-framework dependency. Preserve owned temporary cleanup, isolated inherited environments, local remotes/publication, exact-byte reconciliation, and all-files-before-copy preflight with canonical symlink boundaries. Default fixture copying to recursive hidden-file inclusion with `.git` pruning; support glob strings with portable `/` separators, keep arrays as exact file lists, and reject Git metadata/aliases in either root. Exercise the real packaged lifecycle builder/spec, not a duplicated test configuration. Explicit adapters are not a sandbox for custom commands; see [Testing Custom Workflows](docs/testing.md).

Keep domain `Release` data, immutable execution metadata, and provider clients separate. Never place environments, credentials, or raw event payloads in execution snapshots. Respect scoped provider selection, distinguish unknown steps from skipped ones and outcome from conclusion, isolate histories between invocations, and preserve the original error when failure reporters fail. Test initialization failures and installed portable providers; see [Execution Providers and Contexts](docs/execution.md).

Follow ruby-gem-release's independently idempotent operations from the current checkout and supplied inputs. Reconcile registry checksums, intended Git trees/refs, archive bytes, and hosted outputs; never use `release.json` phases to skip or republish. No saved workflow descriptor or bundle restoration API. Never rewind descendants or overwrite conflicting archives/assets/tags. Gate Actions release on a successful prepublication upload. Test matching and conflicting reruns, fresh intended-release checkouts, ambiguous acceptance, and failed pushes. See [Recovery and Reconciliation](docs/recovery.md).

Keep semantic releases opt-in and numeric/manual-changelog behavior unchanged. Separate history, analysis, selection, and notes services; bind the frozen decision to source/version/notes. Save analysis only for the current Actions invocation, never restore it from downloaded artifacts or cache it on a reusable workflow instance. No eligible changes fail before project edits, not a successful skip. Test reachable/annotated tags, reverts, overrides, source binding, and installed semantic consumers. See [Semantic Releases](docs/semantic.md).

Maintain separate `Test`, `Lint`, and `Package` workflows and Coveralls upload. Use explicit `matrix.entry` lists of compact inline objects, not `include`/`exclude` or Cartesian axes. Type-check runtime and positive/negative contract fixtures; lint TypeScript, JavaScript, YAML, Markdown, embedded JavaScript, and spelling with `npm run lint`. Enforce title-case headings/display names, preserve proper names/expressions, and keep reviewed vocabulary in `.spellcheck.txt`. Run `actionlint .github/workflows/*.yml examples/*.yml` when changing workflow interfaces. JavaScript Danger checks are not configured.

## Documentation and Versions

Keep Markdown paragraphs on one line. Update documentation with behavior; keep DESIGN current and remove superseded proposals rather than writing an implementation diary. Add changelog entries for features, improvements, and fixes, not minor typos or the initial scaffold. Use actual PR numbers and contributor attribution, oldest to newest above the final Next placeholder; predict the number before opening and verify/correct it afterward. See CONTRIBUTING for the exact entry format.

Preserve the editable SVG and generated transparent PNG under `assets/`, their MIT provenance, README-first placement at 160 pixels with alt text, and inclusion in the npm archive. Follow [artwork maintenance](DESIGN.md#artwork) for regeneration and full-size/light/dark rendering checks; do not copy the npm wordmark or embed external resources.

Before changing the version, check the npm registry to establish whether the current version was released; ask if status cannot be established. Keep unreleased versions unchanged, including the initial `0.1.0`. If released, include the bump in the same PR as the change and synchronize `package.json`, `package-lock.json`, and the Next changelog heading. Features in `0.x` increment minor and reset patch (`0.1.1` to `0.2.0`); features in `1.x` and later increment minor while preserving patch (`5.3.1` to `5.4.1`). Breaking changes are allowed within `0.x`: increment minor and reset patch when released, without requesting a major bump. For breaking changes in `1.x` and later, ask before choosing a major bump. Document breaking behavior and migration guidance.

## Git and Publication Safety

Inspect status, branches, and worktrees before switching. Preserve unrelated work. Use topic branches from `master` named `<username>/<topic>` (`dblock` by default), in the existing checkout; use worktrees only for parallel tasks. Prefer one coherent commit per PR. Allow squash or rebase merges, not merge commits. No ordinary development commits/pushes directly to the default branch and never force-push `master`.

Task-owned PR commits may be amended/squashed without asking: verify ownership, record the remote SHA, reconcile remote changes, run local checks, then push with `--force-with-lease=refs/heads/<branch>:<recorded-sha>`. Never rewrite work owned by another contributor. After merges, fetch/prune, verify the merged PR state through GitHub, inspect dirty/untracked and dependent work, switch safely to `master`, and remove only clean, unneeded worktrees and merged local branches. Force-delete a branch only after verifying no unmerged work or dependencies would be lost; never delete active branches or discard work.

Include the Copilot co-author trailer in AI-assisted commits and disclose AI authorship on behalf of `@dblock` in AI-authored PRs/comments. Let closing PR references close issues on merge, not manual issue closure. Never merge, publish, tag, create releases, or set up credentials without explicit authorization; never overwrite published versions or release tags.

Documentation targets `0.1.0`; examples pin the package and Actions interfaces together. Before release work, independently verify actual registry/tag state rather than treating documentation as proof of publication. Keep `self-release.yml` a thin manual caller of the local reusable `release.yml` with `build: true`, not a duplicate pipeline or repository-variable gate. Its publisher filename is `self-release.yml`. Do not dispatch before the initial manual registry release and separately authorized publisher/environment/protection setup are verified. Build the checkout before invoking its CLI, retain the successful prepublication upload boundary, and test the actual reusable-workflow commands against isolated SDK fixtures. Do not store long-lived npm tokens. No direct-push release-automation exception is authorized yet; document any later authorization and protection changes explicitly. See [RELEASING.md](RELEASING.md).

The root `npr.config.js` is this repository's numeric self-release configuration, not a packaged consumer default. Preserve its installed-archive API/CLI validation and test it unchanged against isolated source/packed SDK fixtures; never substitute checkout imports for consumer checks. Its next-development hook pins this package's README/docs installation and Actions references to the released version, not the development version; preserve unrelated references and bytes. Publication always requires explicit authorization. Add an npm version badge only after registry confirmation.
